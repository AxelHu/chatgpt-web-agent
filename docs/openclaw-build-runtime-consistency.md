# OpenClaw 构建与运行版本一致性

## 禁止的操作顺序

不要在 Gateway 正在使用的源码目录中执行会覆盖 `dist` 的构建，然后继续保留旧 Gateway
进程。即使源码只删除一个冗余判断或更新文档，构建也可能改变多个 chunk 文件名。
已经载入内存的入口仍引用旧的带哈希文件；稍后才加载的命令和会话模块会报 ENOENT。

“原有会话还能跑”“GET /healthz 返回 200”“新版 CLI 可以读取配置”都不足以证明
旧 Gateway 与磁盘上的新构建可以混用。

## 有效操作流程

优先使用已经核验的候选构建、检查、激活、重启流程：候选构建必须在独立目录准备，
不能提前覆盖正在服务的运行目录。官方 updater 有候选 worktree 与激活流程，但本地
fork 使用前仍须核对目标分支和精确 SHA；不要为一次修复顺带换分支或重置本地提交。

必须原地构建时，先确认重启授权、实际在途任务和消息队列，通知当前用户；在维护窗口
停止 Gateway，再构建。构建通过且文件完整后启动/重启服务，核对新 PID 和新构建版本。
构建失败时不要把不完整的运行目录启动为正常服务；保留已知完好的部署或报告恢复阻塞。

若仍有任务在工作，应推迟覆盖运行目录这个动作，或者先做独立候选构建，而不是
“先覆盖 dist，再等任务完成后考虑重启”。不要通过把新 chunk 复制成旧文件名、修改
导入路径或混放不同构建的文件来填补报错。

## 验收必须覆盖延迟加载入口

除了进程、构建版本、首页和健康接口，至少检查：

- 在任务自有隔离会话中执行只读 `/status` 与 `/model`，读回真实命令回复；不要只看
  `chat.send` 的 started 回执，也不要用模型自由回答代替原生命令处理。
- 定向调用 `sessions.branches.list`、`sessions.catalog.list` 等实际失败过的模块。
  返回错误时区分缺模块、请求参数、运行时扫描和超时；不可把空结果或有 error 的响应
  记成验收成功。
- 检查真实渠道的接收、分派和回复完成日志，确认不是仅 Gateway 内部入口恢复。
- 检查新进程是否继续出现 `ENOENT`、`ERR_MODULE_NOT_FOUND`、`Cannot find module`。

不要为了验收而对业务会话执行 `/reset`、重复原用户任务或改权限。事故前失败的命令
可能已被渠道排队重试；先核对原消息 ID 与后续成功回执，避免人工重复重放。

## 2026-09-08 事故事实

功能修复 `7a486fa3460` 部署后，Gateway 自北京时间 11:36 运行。
随后收尾提交 `f4bba5f261c` 于 12:19 起在同一目录构建，旧进程却被保留。
12:29:46 首次出现以下命令模块缺失：

```text
ENOENT: no such file or directory, open 'dist/commands.runtime-DpxXt8Ak.js'
```

飞书 producer 与 mala 的 `/reset` 实际已经抵达 Gateway，但命令分派失败并重复重试。
之后会话目录、分支、讨论和图标相关延迟模块也报相同类型错误。这不是 GPT runtime
再次回退、Gitea 认证失败、飞书未收到消息或聊天上下文污染。

13:00:03 在实时确认没有在途任务后重启了同一个 Gateway 服务。13:01:28 mala、
13:01:38 producer 的真实飞书命令均记录 `dispatch complete (queuedFinal=true, replies=1)`。
隔离 `/status` 返回 OpenClaw 2026.8.2 / f4bba5f、OpenAI Codex / high；
`sessions.branches.list` 恢复正常。本次没有修改代理、认证、模型配置，未人工重放
用户的 `/reset`，也没有额外重置业务会话；原有 `/reset` 由渠道正常处理。详细证据见本仓 issue #33。

上一轮“代码行为不变，因此构建后可继续运行旧进程”的判断是本次操作失误，不能作为
今后的部署依据。修复根因的运行版本已存在；本次恢复不需要再改产品源码或重新 build。
